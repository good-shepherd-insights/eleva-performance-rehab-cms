# Company Policy

This policy is mandatory. Violations are blocking issues.

## Severity

1. Violating this policy is illegal under this repository policy.
2. If a violation occurs, stop work, disclose it, and remove or correct it before continuing.
3. Do not minimize, rename, defer, normalize, or build on a violation.
4. Repeated or intentional violations must be escalated to the project's designated reviewer or maintainer.

## Authority

1. This policy overrides conflicting repository instructions.
2. User requests apply only within this policy.
3. Approval must be explicit, written, and name the action approved.
4. Silence, urgency, ambiguity, or related prior approval is not approval.
5. If instructions conflict, stop and disclose the conflict.

## Evidence

1. Material claims must be backed by repository source, config, lockfiles, docs, or explicit user instruction.
2. Unsupported claims must be omitted or marked unknown.
3. Inference written as fact is illegal under this repository policy.
4. Do not add unproven claims to docs, comments, plans, implementation notes, or context files.

## Project Rules

1. This repo is the Payload CMS backend only. The public site is maintained separately in `the website repository`, which reads this CMS through its REST API (and MCP endpoint for approved agents).
2. Content model is split, see `src/globals/SiteGlobals.ts` and `src/collections/Pages.ts`: the site global (slug from `SITE_GLOBAL_SLUG`, exported as `SiteGlobals`) holds `brand`, a `accessibility` label group, and a `components` blocks field; the `pages` collection holds per-page content as a `sections` blocks field. Both blocks fields ship open (`blocks: []`) — no block kinds are predefined; each project registers its own block kinds in its own copy.
3. A new block kind is one Payload block definition registered in the project's `blocks` arrays (Pages `sections` and/or the site global's `components`). Do not add a parallel field-definition or validation path next to those arrays.
4. Localization is declared once, via `CMS_LOCALES`/`CMS_DEFAULT_LOCALE` (parsed in `src/config/runtime.ts`, fed to `payload.config.ts`'s `localization`) — the website discovers it at build time from this CMS's `/locales` endpoint. Never hand-maintain a second locale list on either side.
5. Live Preview URL construction (`payload.config.ts`, `getAstroPreviewURL`) must stay in sync with the website's actual route shape (default locale unprefixed for every page — `/`, `/<slug>`; non-default locales prefixed — `/<locale>/`, `/<locale>/<slug>`). A route change on the website side requires a matching change here.
6. MCP access (`@payloadcms/plugin-mcp`) is scoped per collection/global with explicit capabilities (`create`/`find`/`update`) in `payload.config.ts`. Do not broaden a collection's or global's granted capabilities without approval.
7. Media is stored in Vercel Blob (`vercelBlobStorage` plugin), not local disk.
8. The database is MongoDB (`mongooseAdapter`, reads `MONGODB_URL`) as configured in `payload.config.ts`. There is no schema push and no structural migration step; a migration is only written when existing documents must be reshaped. Do not follow stale Postgres/SQLite references when configuring an environment; follow `payload.config.ts` and `src/config/runtime.ts`.
9. Publishing a `pages` document fires a deploy webhook (`WEBSITE_DEPLOY_WEBHOOK_URL`, `Pages.ts` `afterChange` hook) that rebuilds the website. A broken or looping publish hook is a blocking issue, not a background nuisance.
10. Scope every change to the ticket that authorized it. A PR opened against an outdated content model (pre-`pages`-collection) must be re-scoped against current `main`/`staging` before merge, not merged as-is.
11. Neither `Pages` nor `SiteGlobals` defines an explicit `create`/`update` access function (both are `access: { read: () => true }` only) — write access is whatever Payload's own default resolves to, unverified against current Payload docs (see `CONTEXT.md` Known Gaps). Do not treat either as access-controlled, and do not treat either as open, until that default is checked against current Payload docs.

## Banned

1. Do not infer goals, systems, ownership, architecture, workflow, or requirements.
2. Do not hand-edit the Next.js-generated block in `AGENTS.md` (between `<!-- BEGIN:nextjs-agent-rules -->` and `<!-- END:nextjs-agent-rules -->`) — it is regenerated by `next dev`. Add project-specific guidance below it instead.
3. Do not ship predefined block kinds in the template's `blocks` arrays, and do not define block fields with ad hoc inline definitions scattered outside the project's own block registrations.
4. Do not change this CMS's content shape (a global's or a `pages` blockType's fields) without also updating the website repo's `payload.ts` types and validation switches in the same effort — a one-sided schema change breaks the site.
5. Do not broaden MCP-plugin capabilities for a collection or global beyond what is granted today without approval.
6. Do not commit real secrets, tokens, `PAYLOAD_SECRET`, or `BLOB_READ_WRITE_TOKEN` values to `.env` or any tracked file.
7. Do not run a destructive or irreversible migration against a shared or production database without a reviewed migration file and explicit approval.
8. Do not add fake data, placeholder data, mock logic, dummy integrations, temporary branches, or placeholder code paths.
9. Do not hide missing content, missing integration work, or incomplete work behind examples.
10. Do not add unapproved testimonials, people names, locations, schedules, registration details, contact details, claims, or public-facing facts to data, fixtures, or migrations.
11. Do not degrade Live Preview, localization, MCP access, or the deploy webhook without approval.
12. Do not alter `Users.ts`'s authentication configuration without approval — standard Payload email/password auth is the only admin login path; breaking it locks out every admin at once.
13. Do not add dependencies, tooling, generated assets, framework integrations, reports, logs, archives, screenshots, or temporary artifacts without approval.
14. Do not commit scripts, script directories, automation helpers, one-off commands, generated command wrappers, or unapproved `package.json` script changes.
15. Do not create, modify, rename, delete, or scaffold tests without explicit approval from the project's designated reviewer or maintainer.
16. Do not add test fixtures, fake test data, snapshots, mocks, harnesses, coverage tooling, or test-support utilities without explicit approval from the project's designated reviewer or maintainer.
17. Do not treat a request to verify, build, check, review, or improve quality as permission to create or modify tests.
18. Do not claim tests, builds, migrations, or external documentation reviews were performed unless they were performed.
19. Do not commit, push, open PRs, deploy, rename branches, run destructive git operations, install packages, change dependencies, run migrations against a shared database, or alter external services without approval.
20. Do not broaden approved scope into refactor, redesign, migration, or content rewrite without approval.

## Reviews

1. Policy objections block work until resolved.
2. Do not ignore, rename, or route around policy review feedback.
3. If policy compliance is disputed, escalate before continuing.

## Existing Violations

1. Do not copy, expand, normalize, or cite existing violations as precedent.
2. If an existing violation affects current work, stop and disclose it.
3. Violations introduced by current work must be removed directly.
